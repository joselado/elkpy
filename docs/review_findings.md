# Code review findings: the full-Elk-coverage wrapper

Read-only review of the 64-file, 19,828-line change on branch `elk-full-coverage`
(commit `27afcca`, 2026-09-06), which added 115 `get_*` methods and the ~330-block
input-parameter table. **Nothing here is fixed.** This is a work list.

## Why the review was shaped this way

Almost none of that change had ever been executed. Its task orderings, input blocks
and output-file layouts were transcribed by reading `vendor/elk/src/*.f90`, and its
parsers were unit-tested only against fixtures the same agent wrote from the same
reading -- so a fixture built from a misread `write` statement passes its own test
perfectly, and 438 passing tests say very little. The review therefore cross-checked
Python against the Fortran rather than looking for style or coverage gaps, hunting the
classes that reading can catch: wrong task codes, wrong output filenames, parser
layouts that do not match the actual `write` statement, missing or misordered
prerequisites, unit and factor errors, index-order transpositions, and guards that
pass for the wrong reason.

Seven reviewers (one per module) each produced at most six findings; seven adversarial
verifiers then re-derived every one from the source, instructed to refute when they
could not confirm. **22 raised, 19 confirmed, 3 refuted, 17 unique locations.** No
finding survived as merely plausible -- each was either traced to the source or killed.

Every finding below cites the `vendor/elk/src/` line that proves it. Where the
verifier corrected the original reviewer, the corrected version is what is recorded.

## 1. `src/elkpy/tasks/magnetism_manybody.py:921` -- reuse_epsinv=True is unusable: 601 needs a file it deletes

*missing-prerequisite / verdict CONFIRMED*

**What is wrong.** get_gw_self_energy(reuse_epsinv=True) selects task 601, which skips epsinv and reads an existing EPSINV.OUT, but dispatches through _run_resumed, which unconditionally wipes the run directory — so the file 601 exists to reuse is never present.

**How it fails.** c.get_gw_self_energy(label='gw') completes (hours), leaving workdir/gw/{EPSINV.OUT,GWSEFM.OUT}. c.get_gw_self_energy(reuse_epsinv=True, tempk=1000.0) then calls _run_resumed('gw', [601], ...), whose shutil.rmtree(subdir, ignore_errors=True) (calculation.py:280, no keep/resume parameter exists in the signature at calculation.py:248) deletes both files before elk.in is written. elk.f90:258 `case(600,601) call gwsefm`; gwsefm.f90:40 `if (task /= 601) call epsinv` skips the build; gwsefmk.f90:164 `call getcfgq('EPSINV.OUT',vl,ngrf,nwrf,epsi)`; getcfgq.f90 opens with no status= (UNKNOWN, so an empty file is created) and does `read(245,rec=iq)` with no iostat -> runtime end-of-file abort. NOTE the correction to the reviewer's framing: this is not merely destructive under the same label — under ANY label task 601 is unreachable, since a fresh label gives an empty directory with no EPSINV.OUT and the identical abort. Same-label reuse additionally destroys the expensive prior GWSEFM.OUT/EPSINV.OUT. The module header (lines 20-28) introduces _run_dependent for exactly this hazard and get_spin_spiral_supercell (line 626) guards the analogous task-351 case by requiring resume=True; 601 uses neither.

**Evidence.** src/elkpy/tasks/magnetism_manybody.py:918 `TASK_GW_SELF_ENERGY_KEEP_EPSINV if reuse_epsinv else ...` (line 73: =601) and :921 `subdir = self._run_resumed(label, [task], blocks, ngridk=ngridk)`; src/elkpy/calculation.py:280 `shutil.rmtree(subdir, ignore_errors=True)`; vendor/elk/src/gwsefm.f90:40 `if (task /= 601) call epsinv`; vendor/elk/src/gwsefmk.f90:164 `call getcfgq('EPSINV.OUT',vl,ngrf,nwrf,epsi)`; vendor/elk/src/getcfgq.f90:38-39 open(245,...,access='DIRECT',recl=recl) / read(245,rec=iq)

**Verification.** Read the Python at 912-928 (no guard on reuse_epsinv; _run_resumed is the only dispatch) and calculation.py:248-292 (rmtree is unconditional, no opt-out). Read gwsefm.f90 in full — line 40 is verbatim as quoted and is the only epsinv call; elk.f90:258 confirms 600 and 601 both enter gwsefm. Read getcfgq.f90 in full: the RAM-disk shortcut cannot help across processes, and the file open/read is exactly as cited with no iostat on the read. Verified there is no other code path that could supply EPSINV.OUT. Strengthened the finding: the feature is dead under any label, not only destructive under the reused one.

**Suggested fix.** Route task 601 through this module's own `_run_dependent()` (the non-wiping mode written for exactly this), or refuse `reuse_epsinv=True` unless the target directory already holds `EPSINV.OUT` -- the guard `get_spin_spiral_supercell` already applies to task 351 at line 626.

## 4. `src/elkpy/tasks/spectra.py:494` -- get_core_wavefunctions() crashes on H, He or Li

*correctness / verdict CONFIRMED*

File is entirely new in this diff (+1382 lines). Severity medium is right: it is a hard crash but confined to one method and one class of light-element structures, with no silent wrong number.

**Suggested fix.** Skip atoms whose `WFCORE` file is empty rather than letting `parse_wfcore()` raise, and return the heavy atoms' data. A species with no `spcore` state is normal input, not an error.

## 5. `src/elkpy/tasks/phonons.py:630` -- LAMBDAQ couplings are half the lambda in the same dict

*misleading-docs / verdict CONFIRMED*

**What is wrong.** The 'couplings' returned from LAMBDAQ.OUT are exactly half the standard Allen lambda_{q,nu} and half the 'lambda' returned beside them, because writelambda.f90 divides by pi*fermidos (the TOTAL, both-spin DOS) where alpha2f.f90 uses fermidos/2; the docstring writes the standard Allen formula with N(e_F) left undefined and calls the factor unsettled when it is exactly 2 and derivable from three Fortran lines.

**How it fails.** A user takes result['couplings'] from get_superconductivity() -- which returns 'couplings' and 'lambda' in ONE dict, with no normalisation warning in its own docstring (only 'FORMAT-DERIVED') -- sums over branches and q-weights and feeds it to McMillan/Allen-Dynes. The value is half the true lambda; for Nb (Elk's own shipped MCMILLAN.OUT gives 1.0534) they would use ~0.53, which with mu*=0.15 drops T_c by roughly an order of magnitude while looking entirely plausible.

**Evidence.** vendor/elk/src/occupy.f90:94 `fermidos=fermidos*occmax*t0` (comment :84-85 'in units of states/Hartree/unit cell'), with init0.f90:130/133 occmax=1 if spinpol else 2 -> fermidos is the TOTAL both-spin DOS; vendor/elk/src/writelambda.f90:25 `t1=pi*fermidos*wphq(i,iq)**2`; vendor/elk/src/alpha2f.f90:99 `t1=twopi*(fermidos/2.d0)*dw*dble(ngrkf)**3`; vendor/elk/src/ephcouple.f90:136 `t1=pi*wkptnr*occmax`; vendor/elk/examples/phonons-superconductivity/Nb-DFPT/MCMILLAN.OUT lambda=1.053424300.

**Verification.** Settled from source, including the one escape route the reviewer did not close: if Elk's gamma were per-spin, dividing by the total DOS would compensate and there would be no factor. It is not -- ephcouple.f90:136 multiplies the linewidth accumulator by occmax, so GAMMAQ carries the spin sum and is the full Allen linewidth; dividing that by pi*fermidos = pi*2*N_spin therefore gives exactly half the Allen lambda_qnu, while alpha2f's 2*pi*N_spin is the standard alpha^2F normalisation, and the shipped Nb MCMILLAN.OUT (1.053, the accepted value) confirms the alpha^2F side is the standard one. Reviewer's line numbers all check out by count; the ephcouple `t1=pi*wkptnr*occmax` line is 136, not 131 (131 is the putephmat guard). Downgraded from high to medium and recategorised: no returned NUMBER is wrong -- 'couplings' is a faithful read of LAMBDAQ.OUT -- and get_electron_phonon_coupling's docstring (lines 670-675) does name both normalisations and warn against a naive q-average. What survives is that the docstring states lambda_qnu = gamma/(pi N(e_F) omega^2) with N(e_F) undefined, which any reader takes as the per-spin DOS of the standard Allen formula, and calls the factor unsettled when it is provably 2; and that get_superconductivity() hands back both keys with no warning at all. Fix is one docstring line plus a note on get_superconductivity, not a code change.

**Suggested fix.** Multiply the `LAMBDAQ.OUT` couplings by 2 to match the `lambda` returned beside them, or rename the key and document the factor. The docstring's `N(e_F)` must be defined as the total both-spin DOS, and the 'unsettled' note removed -- it is settled.

## 6. `src/elkpy/tasks/groundstate.py:269` -- get_stress() pressure ignores Structure.scale (off by scale^2)

*wrong-units / verdict CONFIRMED*

**What is wrong.** get_stress() converts Elk's dE/dt into a hydrostatic pressure using the raw, unscaled Structure.avec, but Elk multiplies avec by the `scale` input before doing any physics, so the returned pressure is wrong by a factor of scale^2 whenever scale != 1.0.

**How it fails.** Structure(avec=[[0,0.5,0.5],[0.5,0,0.5],[0.5,0.5,0]], scale=10.26) -> get_stress() goes through _run_standalone (groundstate.py:162-169), which calls _add_base_blocks; that writes `scale 10.26` as its own block and `avec` raw (calculation.py:141-143). readinput.f90:2275 then does avec(:,:)=sc*avec(:,:), so genstrain builds strain(:,:,1)=A_elk/||A_elk|| and genstress returns dE/dt in that scaled frame. pressure_from_stress(stress, avec) is then handed A_python = A_elk/sc, so it uses ||A_elk||/sc and V_elk/sc^3 and returns P_true * sc^2 (105x for scale=10.26). The guard on line 268 cannot catch it: isotropic = avec/||avec|| is scale-invariant, so it matches strain(:,:,1) exactly and the wrong number is returned instead of None. Only result["pressure"] is affected; result["strain"]/result["stress"] are Elk's own output and are fine. The repo's own tests use a scaled Structure (tests/test_calculation_moke.py:32 `scale=3.33`), so the trigger is ordinary usage, not hypothetical.

**Evidence.** vendor/elk/src/readinput.f90:2274-2275 `! scale and rotate the lattice vectors` / `avec(:,:)=sc*avec(:,:)`; vendor/elk/src/genstrain.f90:12-13 `t1=norm2(avec(1:3,1:3))` / `strain(1:3,1:3,1)=avec(1:3,1:3)/t1`; src/elkpy/parsers/stress.py:139-142 uses the caller-supplied avec for both `abs(np.linalg.det(avec))` and `np.linalg.norm(avec)`; src/elkpy/calculation.py:141-143 writes `scale` as a separate block and `avec` unscaled; and the rest of the package consistently does apply the factor -- calculation.py:1348 `* self.structure.scale**3`, calculation.py:2238 and exchange.py:62,325 `np.array(structure.avec) * structure.scale` -- making groundstate.py:266 the lone outlier.

**Verification.** Read groundstate.py:260-272, parsers/stress.py:119-142, calculation.py:120-160, structure.py:45-52 (avec stored verbatim, scale stored separately), and groundstate.py:144-169 to confirm _run_standalone routes through _add_base_blocks. Read readinput.f90 around 2260-2290 and genstrain.f90 in full myself; both say what the finding claims. Algebra re-derived independently: P_computed/P_true = (||A||/sc)/(V/sc^3) / (||A||/V) = sc^2. Guard is scale-invariant as claimed. Confirmed as reported, at the reported line.

**Suggested fix.** Pass the scaled lattice vectors to `pressure_from_stress`, i.e. apply `Structure.scale` the way `readinput.f90:2275` does (`avec = sc*avec`) before computing the volume and norms.

## 7. `src/elkpy/tasks/groundstate.py:790` -- MD restart guard misses ATDVC.OUT; stale trajectory returned as new

*guard-that-does-not-guard / verdict CONFIRMED*

**What is wrong.** The restart=True path is the one non-wiping run mode, and its precondition check tests only TIMESTEP.OUT (line 790) even though its own error message at line 793 names ATDVC.OUT; if ATDVC.OUT is absent or the time grid changed, moldyn hits a bare Fortran `stop` (exit status 0), the launcher does not raise, and the previous run's untouched *_TD.OUT files are parsed and returned as if the restart had run.

**How it fails.** Concrete trigger: get_molecular_dynamics(tstime=5.0) with Elk's defaults dtimes=0.1, ntsforce=100. gentimes.f90:18 gives ntimes=nint(5/0.1)+1=51; moldyn.f90:63 loops `do itimes=1,50,100`, i.e. one iteration; atptstep.f90:17-18 computes itn=1+100=101 > 51 and returns before `call writeatdvc`, so ATDVC.OUT is never written -- while writetimes (moldyn.f90:85) still writes TIMESTEP.OUT. A later get_molecular_dynamics(restart=True) then passes the line-790 guard, writes a task-421 elk.in into the un-wiped subdirectory, and moldyn.f90:36-43 sets trdatdv=.true. and calls readatdvc, which does write(*,...) + bare `stop` on the missing file. I compiled a one-line gfortran program to check: a bare `stop` after a write exits 0. launcher.py:120 only raises on returncode != 0, and nothing checks INFO.OUT here, so control returns normally; because the directory was deliberately not wiped, TOTENERGY_TD.OUT / FORCEMAX_TD.OUT / FORCETOT_TD.OUT / ATDISP*_TD.OUT from the first run are still present (moldyn.f90:47-59 deletes them only when tdt0, i.e. task 420) and are parsed -- the caller receives the previous trajectory with no error. The same silent path is reached if dtimes is changed between runs (readtimes.f90:32-40 bare `stop` on a differing time step); changing only tstime is safe, since times(its)=(its-1)*dtimes is unchanged.

**Evidence.** src/elkpy/tasks/groundstate.py:789-793 checks only _file("md_timestep") while the raised message says "(TIMESTEP.OUT and ATDVC.OUT)"; vendor/elk/src/readatdvc.f90:11-17 `open(50,file='ATDVC.OUT',...,status='OLD',iostat=ios)` then `stop`; vendor/elk/src/atptstep.f90:17-18 `itn=itimes+ntsforce` / `if (itn > ntimes) return` skipping line 34's `call writeatdvc`; vendor/elk/src/moldyn.f90:47-59 (files deleted only under tdt0) and :82-85 (atptstep before writetimes); vendor/elk/src/readtimes.f90:32-40; src/elkpy/launcher.py:120-123 is the only failure detection. Note that adding an ATDVC.OUT existence check fixes the missing-file case but not the changed-dtimes case -- that needs a post-run check that TIMESTEP.OUT advanced, or a scan of elk.out for "Error(".

**Verification.** Read groundstate.py:786-828 and launcher.py:100-125; read moldyn.f90, readatdvc.f90, atptstep.f90, readtimes.f90, writetimes.f90, writeatdvc.f90 and gentimes.f90 in full rather than trusting the quoted snippets -- every cited statement is present as claimed (line numbers shifted by 1-2 from the finding's). The one claim not readable off the source, that a bare Fortran `stop` exits 0, I verified by compiling and running a trivial gfortran program (exit=0); the launcher's own docstring independently notes elk exits 0 on internal errors. Also re-derived the loop arithmetic to produce a trigger that really does skip writeatdvc, since a single force step does NOT always skip it (ntsforce = ntimes-1 gives itn = ntimes, which still writes).

**Suggested fix.** Check `ATDVC.OUT` (what the error message already names) rather than `TIMESTEP.OUT`, and make the launcher treat a bare Fortran `stop` on a restart as a failure -- exit status 0 with untouched output currently reads as success.

**How it fails.** Call get_structure_factors(vhmat=[[1,1,0],[0,1,0],[0,0,1]]). groundstate.py:525 writes the block row by row and readinput.f90:1414-1417 reads vhmat(1,:), vhmat(2,:), vhmat(3,:), so Elk's transform uses the matrix as written. sfacrho.f90:43-45 then prints vhmat(:,1)/(:,2)/(:,3) -- the columns -- one per line, and sfac.py:60 stacks those lines as rows, so result["vhmat"] is M^T. A caller who round-trips or compares result["vhmat"] against the matrix they passed sees a silently different matrix; a diagonal (default) vhmat hides it entirely. Impact is bounded: no elkpy code path consumes result["vhmat"], the raw integer ivh indices are never returned (only the already-transformed "hkl"), so it cannot be misapplied inside the package, and no test pins input-vs-output (tests/test_parsers_sfac.py builds synthetic files only). The residual defect is an API surface that returns something other than what was passed in, under the same key name, with the explanation buried in the parser module.

**Evidence.** vendor/elk/src/sfacrho.f90:43-45 `write(50,'(3G18.10)') vhmat(:,1)` / `vhmat(:,2)` / `vhmat(:,3)` vs vendor/elk/src/readinput.f90:1414-1417 `read(50,*,err=20) vhmat(1,:)` / `vhmat(2,:)` / `vhmat(3,:)`; sfacrho.f90:50-52 `v(:)=vhmat(:,1)*dble(ivh(1,ih))+...` confirms the transform uses the as-input (row-read) matrix; src/elkpy/tasks/groundstate.py:525 `blocks["vhmat"] = [tuple(row) for row in vhmat]` writes rows; src/elkpy/parsers/sfac.py:49-53 documents the as-printed choice, whose stated rationale ("the file is only ever a record of the input setting, so it is returned as printed") is what makes it a defect rather than a convention -- as printed, it is not a record of the input setting.

**Verification.** Opened sfacrho.f90 and readinput.f90 myself: the column-print/row-read asymmetry is real exactly as cited, and groundstate.py:525 writes rows, so the input matrix is what Elk applies and the returned matrix is its transpose. I considered refuting on the grounds that sfac.py:49-53 documents the as-printed layout deliberately, and downgraded severity accordingly, but every factual claim holds, the public get_structure_factors docstring gives no hint, and the parser docstring's own rationale contradicts itself -- so this is a real (if low-impact) API defect, not a reviewer misreading. Verified the blast radius is limited: grep shows no consumer of result["vhmat"] anywhere in src/ or tests/, and raw ivh is never exposed.

**Suggested fix.** Transpose in `parse_structure_factors` so the returned `vhmat` matches the matrix the caller passed, or document the difference on `get_structure_factors` itself, not only on the parser.
