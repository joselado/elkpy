# Vertical tunnelling transport through monolayer graphene

Runs directly from `elk.in`, the same way any example under
`vendor/elk/examples/` does:

```bash
cd examples/vertical-transport
../../build/elk/src/elk         # ~2 minutes
python3 plot_transport.py       # writes transport.png
```

It needs an `elk` built by `build_elk.sh`, which applies
`patches/0012-vertical-transport.patch` — task 9005 and the
`elkpy_transport_*` blocks are elkpy extensions, not stock Elk.

## What it computes

An STM image answers "what does the tip see?". This answers "what gets
through?". The electron enters at a point **r** above the sheet and leaves
into an infinite metallic plane below it, so the current is set not by the
local density of states at the tip but by the **nonlocal** Green's function
between the two:

```
T(r; E) = int_plane |G(r, r'; E)|^2 d^2r'
G(r, r') = sum_kn psi_kn(r) psi*_kn(r') / (E - eps_kn + i eta)
```

The substrate is invariant under every lateral lattice translation, so lateral
momentum is conserved: routes at different **k** cannot interfere, routes at
the *same* **k** can. What survives is one Hermitian matrix per k-point — the
bands' Gram matrix restricted to the exit plane — and one quadratic form:

```
S_k[n,n'] = int_plane psi*_kn psi_kn'
T(r; E)   = sum_k w_k sum_nm a_n(r) a*_m(r) S_k[n,m]
```

Task 9005 writes `S_k` and the tip amplitudes `psi_kn(r_p)`. The energy
weighting and the contraction are done in Python
(`elkpy.parsers.transport`) rather than in Fortran — deliberately, so the
arithmetic is unit-testable against synthetic data and an energy sweep costs
nothing extra, neither the wavefunctions nor `S_k` depending on the energy.

## Why the monolayer gives the same picture twice

For one sheet the answer is a theorem, not an observation. The states at the
Fermi level are the Dirac doublet at **K**, and the symmetry the tip/substrate
geometry leaves intact is C<sub>3v</sub> — whose mirror σ<sub>v</sub> exchanges
the two sublattices *without* flipping z, so it survives the geometry and the
doublet is still an irreducible 2D representation. By Schur's lemma
`S_K` restricted to it is a multiple of the identity: the substrate cannot tell
the two partners apart, there is nothing off-diagonal for the current to
interfere through, and the transmission collapses onto the tunnelling image.
The script prints that as `weight off S_k's diagonal` (7e-7 here) and a
correlation of 1.000000 between the two maps.

Stack a second layer AB (Bernal) and it stops being true: the element that
exchanges the low-energy partners is then a *z-flipping* in-plane C₂′, which
the geometry breaks, the states become layer-polarized, and the current — which
has to cross both sheets — sees something no surface density of states
contains.

## Things worth changing

- the third number in each `plot2d` line, and `elkpy_transport_exit`'s second
  number — the tip height and the substrate depth. Both must stay in the
  vacuum, outside every muffin-tin sphere (the task checks and refuses), and
  `rgkmax` sets how far into the tail the plane-wave representation is still
  meaningful, so do not retract the tip arbitrarily far.
- `elkpy_transport_kgrid` — it is generated by the task itself, so it is
  independent of `ngridk` and of `reducek`. **It must be a multiple of 3**:
  graphene's states at E<sub>F</sub> all sit at K, and a mesh without K gives
  a map that is identically zero rather than merely small.
- `elkpy_transport_window` plus `broadening=` in the script — the window is
  what gets exported, the broadening is the energy width the leads let states
  through in.
- `elkpy_transport_spol` / `elkpy_transport_sdir` — a *magnetic* substrate,
  which accepts `1 + P n·σ`. This is the spin-space sibling of the magnetic
  *tip* in `examples/spin-stm`, but it sits inside the overlap integral rather
  than being applied to a density. Needs a spin-polarised run.

`tshift .false.` is mandatory and is not stylistic: Elk otherwise relocates
the origin (onto the inversion centre — for a honeycomb, the bond midpoint)
while both plotting planes stay in the frame written in `elk.in`.

The same calculation from Python is `Calculation.get_vertical_transport()`;
see `notebooks/20_vertical_transport.ipynb`.
